# Personalized booking contracts

New website bookings prepare a contract from the saved customer name/email/phone, wedding date, venue, preferred start time, guest count, collection/extras, server-calculated amount, prepayment percentage, balance deadline and the owner's existing agreement/cancellation text. No legal clauses are generated by an AI or silently added to the configured terms.

## Customer flow

Choose a date and enter details, then select **Generate my contract**. The private booking portal presents the generated copy before payment. The customer types their full name and explicitly confirms electronic-signature intent. The app saves the exact document, its SHA-256, contract revision, signer name, booking email, server timestamp, consent wording and a bounded browser description. Signing alone never records a payment or confirms a date. New online invoices are blocked until the current contract is signed.

Quote/travel-review and waitlist requests do not create an immediately signable final contract. Once the owner offers a quote, the customer signs the priced contract while accepting that quote; capacity is checked in the same transaction before a date hold is committed.

## Saved copies and revisions

The customer and authenticated merchant can view the saved signature and print/save a PDF through the browser. Printing opens an escaped, self-contained copy in an about:blank tab, avoiding private booking-link query parameters in print headers. No customer documents are published in GitHub or a public assets directory.

Approved changes to the date, venue, guest count or other signed document fields preserve the earlier signed copy in contract history, create an unsigned revision and require another signature before a new invoice. Outstanding invoice work must be voided before changing signed contract details; the feature does not silently revoke external Shopify invoices. Payment receipts do not change the signed document. Changing global settings does not rewrite existing saved agreement text.

Existing checkbox acceptance remains labeled as earlier acceptance; it is not fabricated into a typed signature. Existing paid or manually entered legacy records are not automatically marked signed or forced through a migration. Owner-created records also have a generated copy, but their existing acceptance/payment behavior is preserved unless a typed signature is taken. The new online flow explicitly requires signing.

## Access and storage

Contracts and signatures use the existing booking details JSON and owner activity record; no schema migration, added Shopify scope or external signing subscription is required. Signing uses the existing private, expiring/revocable booking link and same-origin POST check. The link is checked again inside the booking lock. Posted prices, email addresses, timestamps and agreement wording cannot replace server data. Stale document hashes, missing name/consent, cross-store access and attempts to replace a saved signer are rejected. Identical signature retries retain the original timestamp and do not duplicate activity.

This is the app's own typed-name signature record, not an identity-verified signing certificate from an external provider. The existing owner-approved agreement text remains the contract's terms.

## Validation and release

Unit checks cover personalization, exact 30/70 amounts, required consent, stale hashes, replay, signed-copy history, legacy acceptance and escaped/token-free print HTML. Transactional tests cover private-link access, invoice gating, quote acceptance and amendments. The existing booking/payment/calendar/email suites and clean build/typecheck are run by Booking source checks.

This feature is source-only until the changed booking app is deployed to Azure. No live customer booking, signature, email, invoice or payment was created during implementation. `PRODUCTION-SOURCE.json` remains the historical pre-contract deployment/source baseline; it does not certify this new feature as deployed.

Owners can explicitly select **Prepare contract & require customer signature** for an older unsigned booking. This retains any earlier checkbox-acceptance record, uses existing saved terms (or current configured terms if none were saved), and requires a real customer signature. Pending invoice work must be voided first; this button never signs on behalf of the customer.
